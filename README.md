# Front Row Ticket Upgrade Challenge

## วิธีเปิดใช้งานและทดสอบ (Quick Start)

### สิ่งที่ต้องมีในเครื่อง
- Node.js เวอร์ชั่น 18 ขึ้นไป (โปรเจกต์นี้ทดสอบบน Node v22)
- npm เวอร์ชั่น 9 ขึ้นไป

### 1. ติดตั้งแพ็กเกจ
```bash
npm install
```

### 2. รันชุดทดสอบ (Automated Tests)
รันแบบทดสอบทั้งหมด 10 ข้อ (ครอบคลุมทั้งกฎของระบบและเทสความเร็ว 100,000 รายการ):
```bash
npm test
```
หรือถ้าระหว่างแก้โค้ดอยากให้รันเทสอัตโนมัติ:
```bash
npm run test:watch
```

### 3. เปิดหน้าจอ UI จำลองคิว
เปิดหน้าเว็บเพื่อทดลองกดเร่งเวลา, สลับโหมด, และดูการคำนวณคะแนนแบบสดๆ:
```bash
npm run dev
```
จากนั้นเปิดเบราว์เซอร์ไปที่ `http://localhost:5173`

### 4. สั่งบิลด์ (Production Build)
```bash
npm run build
```

### 1. สูตรคิดคะแนน (Priority Score) ทำงานอย่างไร?

เราออกแบบคะแนนโดยบาลานซ์ระหว่าง **"คนที่อดทนรอนาน"** กับ **"แฟนตัวจริงที่ซัพพอร์ตศิลปิน"** ตามสูตรนี้ครับ:

$$\text{คะแนนรวม} = \text{แต้มเวลารอ} + \text{โบนัสรอนาน} + \text{แต้ม Loyalty} + \text{โบนัส VIP} + \text{แต้มราคาตั๋ว} - \text{แต้มตัดสิทธิ์คนเพิ่งได้}$$

- **เวลารอคิว (ประมาณ 0.5 แต้มต่อนาที หรือ 30 แต้มต่อชั่วโมง)**: ยิ่งมาก่อนและนั่งรอในคิวนาน ก็ยิ่งได้แต้มสะสมเยอะขึ้น
- **โบนัสคนรอนานพิเศษ (+20 แต้ม)**: ถ้าใครนั่งรอเกิน 2 ชั่วโมงขึ้นไป เราจะแจกแต้มปลอบใจก้อนนี้เพิ่มให้ เพื่อไม่ให้คนเพิ่งมาใหม่แซงคิวไปได้ง่ายๆ
- **Loyalty Points (ได้ 1 แต้ม ต่อทุกๆ 10 พอยต์)**: ให้เกียรติแฟนพันธุ์แท้ที่สะสมพอยต์กับแพลตฟอร์มมาตลอด (เช่น มี 500 พอยต์ ได้เพิ่ม +50 แต้ม)
- **สถานะ VIP (+25 แต้ม)**: มีคะแนนพิเศษให้สำหรับคนที่เป็นสมาชิกระดับ VIP
- **ราคาตั๋วที่ซื้อ (+0.05 แต้ม ต่อ 1 ดอลลาร์)**: ให้ความสำคัญกับคนที่ยอมจ่ายซื้อตั๋วราคาแพงกว่าเล็กน้อย
- **หักแต้มคนเพิ่งได้ไป (-20 แต้ม ต่องวดที่เคยได้ใน 30 วัน)**: ป้องกันไม่ให้คนเดิมๆ ได้ตั๋วหน้าเวทีซ้ำแล้วซ้ำเล่า เพื่อกระจายความสุขให้คนอื่นบ้าง

ที่สำคัญคือ **มีคำอธิบายชัดเจนทุกแต้ม** ผู้ใช้สามารถกดดูได้ทันทีว่าคะแนนแต่ละแต้มมาจากไหน บวกหรือลบเพราะอะไร โปร่งใสตรวจสอบได้ 100%

### 2. ป้องกันไม่ให้คนปั๊มหลายบัญชี (Fan Group) โกงระบบได้อย่างไร?

ถ้ามีใครหัวหมอ เปิด 5 บัญชี เพื่อหวังจะมีชื่อสุ่ม 5 เท่า ระบบเราจะจัดการด้วยวิธีนี้ครับ:

1. **สืบหาความเชื่อมโยง (Grouping)**: เราจับคู่บัญชีที่มีข้อมูลตรงกัน ไม่ว่าจะเป็น เบอร์โทรศัพท์ (ทำความสะอาดตัดขีด/เว้นวรรคแล้ว), รหัสเครื่อง (Device ID) หรือ บัญชีที่ใช้จ่ายเงิน 
   - และที่สำคัญคือ **"สืบต่อได้หลายทอด"** เช่น นาย A ใช้เบอร์เดียวกับ นาย B และ นาย B ใช้เครื่องเดียวกับ นาย C ระบบจะรู้ทันทีว่าทั้ง A, B, C คือคนๆ เดียวกัน
2. **เลือกตัวแทนกลุ่มคนเดียว (1 กลุ่ม = 1 สิทธิ์)**: ภายในกลุ่มบัญชีที่เชื่อมกัน เราจะเลือกเฉพาะ **"บัญชีที่ดีที่สุดเพียงบัญชีเดียว"** (คนที่ได้คะแนนสูงสุด) ขึ้นมาเป็นตัวแทน ส่วนอีก 4 บัญชีที่เหลือจะถูกตัดทิ้ง ไม่ได้สิทธิ์ลุ้น แปลว่า ต่อให้เขาสมัครมา 100 บัญชี เขาก็ได้สิทธิ์ลุ้นตั๋วแค่ 1 ใบเท่ากับคนอื่น
3. **ส่งต่อประวัติการอัปเกรด (กันชุบตัว)**: ถ้าบัญชีเก่าเคยได้ตั๋วไปแล้วเมื่อวาน แล้ววันนี้แอบสมัครบัญชีใหม่เอี่ยมมาลุ้น ระบบจะดึงประวัติการอัปเกรดจากบัญชีเก่ามาหักคะแนนบัญชีใหม่ด้วย ทำให้ไม่สามารถเปิดไอดีใหม่เพื่อล้างประวัติได้เลย

### 3. ถ้าคะแนนเท่ากันเป๊ะ ตัดสินแพ้ชนะอย่างไร? (Tie-breaking)

ระบบนี้ **ห้ามใช้การสุ่ม (Random)** เด็ดขาด เพื่อให้รันกี่ครั้งด้วยข้อมูลเดิม ก็จะได้ผู้ชนะคนเดิม 100% เสมอ

ถ้าคะแนนออกมาชนกันพอดี เราจะใช้เกณฑ์ตัดสินตามลำดับนี้ครับ:
1. **ใครมาก่อนชนะ (FIFO)**: ดูเวลาที่กดเข้าคิว ใครกดเข้ามาก่อน ได้ไปก่อน
2. **Loyalty Points สูงกว่า**: ถ้าเวลาเข้าคิวเท่ากันเป๊ะ ใครสะสมแต้มกับเรามาเยอะกว่า ชนะ
3. **ซื้อตั๋วแพงกว่า**: ถ้าแต้มยังเท่ากันอีก ใครซื้อตั๋วมาแพงกว่า ชนะ
4. **เรียงตามรหัส ID (Alphabetical)**: ถ้าทุกอย่างข้างบนตรงกันหมด จะใช้รหัสประจำตัว Entry ID เทียบตามตัวอักษร A-Z เพื่อให้ได้ผลลัพธ์ที่นิ่งและแน่นอนเสมอ

### 4. ประสิทธิภาพและความเร็วของระบบ (Time Complexity) เป็นอย่างไร?

ขั้นตอนการจัดกลุ่มบัญชีทั้งหมด ทำงานได้เร็วระดับ **เส้นตรงเกือบ $O(N)$** ครับ

- **ทำไมถึงไม่ช้า?**: ทั่วไปถ้าเขียนง่ายๆ เรามักจะเอาข้อมูลทุกคนมาวนลูปเทียบกันทีละคู่ ($O(N^2)$) ซึ่งถ้ามีคนเข้าคิว 500,000 คน ระบบจะต้องคำนวณถึง 250,000,000,000 ครั้ง โน้ตบุ๊กค้างแน่นอน
- **สิ่งที่เราทำ**: เราใช้ **Hash Map** คู่กับโครงสร้างข้อมูล **Union-Find (Disjoint-Set)** พออ่านข้อมูลคนเข้ามาปุ๊บ ก็จับโยงเข้ากลุ่มได้ทันทีแบบ $O(1)$ 
- **ผลลัพธ์จริง**: ทดสอบกับข้อมูล **100,000 รายการ ใช้เวลาประมวลผลประมาณ 1.0 วินาทีเท่านั้น** บนเครื่องโน้ตบุ๊กทำงานทั่วไป ไม่กินแรมและไม่กระตุกครับ

### 5. มีเคสไหนบ้างที่ระบบนี้อาจจะยังดู "ไม่ค่อยแฟร์"?

**เคส: คนในบ้านใช้ iPad หรือบัตรเครดิตใบเดียวกัน**

สมมติคุณพ่อกับคุณลูกเป็นแฟนเพลงทั้งคู่ ซื้อตั๋วคนละใบและตั้งใจไปดูด้วยกัน แต่คุณพ่อใช้ iPad เครื่องเดียวกันให้ลูกกดเข้าคิว หรือใช้บัตรเครดิตของคุณพ่อจ่ายเงินให้ทั้งสองคน:
- ระบบตรวจจับอัตโนมัติจะมองว่า 2 บัญชีนี้เป็น "คนเดียวกันที่แอบปั๊มแอคเคานต์"
- ผลคือระบบจะยุบรวมให้เหลือสิทธิ์ลุ้นเพียงคนเดียว และตัดสิทธิ์อีกคนทิ้งไปโดยปริยาย

*ทางแก้ในชีวิตจริง*: ควรมีปุ่มให้กด "ยืนยันตัวตนคนละคน" เช่น ส่ง SMS OTP คนละเบอร์ หรือให้ถ่ายรูปบัตรประชาชนยืนยัน เพื่อปลดล็อกให้แยกกลุ่มกันได้

### 6. โหมดพิเศษทั้ง 3 โหมด (Rush Hour, VIP Hour, Fair Queue Mode) ทำงานอย่างไร?

| โหมด | สิ่งที่ระบบปรับเปลี่ยน | ผลลัพธ์ที่ได้ |
| :--- | :--- | :--- |
| **Rush Hour** | เพิ่มน้ำหนักของเวลารอเป็น $3\times$ (จากนาทีละ 0.5 เป็น 1.5 แต้ม) | เหมาะกับช่วงคนแห่กันมาเยอะๆ โหมดนี้จะให้รางวัลกับคนที่นั่งทนรอในแถวมานานที่สุด |
| **VIP Hour** | เพิ่มแต้มพิเศษให้ VIP จาก +25 เป็น +60 แต้ม | เอาไว้จัดแคมเปญช่วงสั้นๆ เพื่อเอาใจและตอบแทนแฟนๆ ที่เป็นสมาชิก VIP |
| **Fair Queue Mode** | เพิ่มบทลงโทษคนเพิ่งได้ตั๋ว จากหัก -20 เป็นหักหนักถึง -50 แต้ม | ช่วยกระจายโอกาส คนที่เคยได้อัปเกรดไปเร็วๆ นี้จะแทบไม่มีสิทธิ์ลุ้นเลย เพื่อเปิดทางให้คนที่ไม่เคยได้ตั๋วหน้าเวทีมีโอกาสชนะสูงขึ้นมาก |

### 7. ถ้ามีเวลาทำต่อ อยากพัฒนาอะไรเพิ่มอีก?

1. **วาดกราฟเครือข่ายบัญชี (Graph Visualization)**: ทำภาพกราฟิกแสดงจุดและเส้นโยงให้เห็นชัดๆ เลยว่า บัญชีไหนแอบผูกกับบัญชีไหน ผ่านเบอร์หรือเครื่องอะไร ดูง่ายขึ้นเยอะ
2. **อัปเดตแบบเรียลไทม์ (Live WebSocket / SSE)**: มีคนเข้าคิวปุ๊บ หน้าจอขยับทันทีแบบสดๆ ไม่ต้องคอยกดรีเฟรช
3. **ระบบแคชกลุ่ม (Smart Group Cache)**: เวลาเวลาเดินหน้าไป 5 นาที ไม่ต้องมานั่งจับกลุ่มคนแสนคนใหม่ตั้งแต่ศูนย์ แค่คำนวณแต้มเฉพาะคนที่เปลี่ยนสถานะ
4. **ตรวจจับบอทด้วยพฤติกรรม (Bot Detection)**: เช็กความเร็วในการกด, IP Address และลายนิ้วมือเบราว์เซอร์ เพื่อดักจับโปรแกรมบอทที่พยายามสแปมคิว
